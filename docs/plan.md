# Agent Drive — Build Plan (v1)

Scope: the v1 stories in [user-stories.md](user-stories.md). Story IDs below
(S1.1 etc.) refer to that file. This plan is written for the agent that builds
the product. Choices marked **default** are recommendations; the builder may
change them with a short written reason in the PR.

## Architecture

```
 agent / MCP client            developer / operator        share recipient
        |                              |                          |
  agent-drive (npm)              web console (browser)      share page (browser)
  - stdio MCP server             - decrypts in browser      - decrypts in browser
  - CLI                                |                          |
  - client library                     |                          |
  - encrypts / decrypts                |                          |
        |   HTTPS + API key            |                          |
        +--------------> Agent Drive API (Next.js on Vercel) <----+
                          - accounts, agents, drives, API keys
                          - file + version metadata (Postgres)
                          - presigned S3 URLs, quotas, audit, billing
                                   |                 |
                              Postgres            Amazon S3
                         (metadata only)     (ciphertext only)
```

Bytes never pass through the API: clients upload and download ciphertext
directly to S3 with presigned URLs. The API stores metadata and authorizes.

### Defaults

- **Language / repo:** TypeScript, pnpm workspace, two packages:
  `apps/web` (Next.js App Router: API routes, console, share page) and
  `packages/agent-drive` (one npm package: library, CLI, stdio MCP server).
- **Database:** Postgres (Neon through the Vercel Marketplace), Drizzle for
  schema and migrations.
- **Object storage:** Amazon S3 via AWS SDK v3. MinIO in Docker for local
  development and opt-in Actions verification.
- **Auth for humans:** Clerk (GitHub OAuth provider if configured). **Auth for
  agents:** API keys, stored hashed, shown once.
- **Billing:** Stripe (subscriptions + metered usage), test mode in local tests.
- **MCP:** official `@modelcontextprotocol/sdk`, stdio transport.
- **Tests:** Vitest for unit and integration, Playwright for console and share
  page, and a local `pnpm verify` gate; GitHub Actions are manually dispatched.

### Encryption design (default)

- Each drive has a 32-byte **drive key**, generated by the client, never sent to
  the server. Supplied to agents as `AGENT_DRIVE_KEY_<drive>` or a key file.
- Each file version gets a random 32-byte **file key**. Contents are encrypted
  with AES-256-GCM in 1 MiB chunks; each chunk's nonce is derived from a random
  base nonce plus the chunk index, and the chunk index and a final-chunk flag
  are bound as additional authenticated data, so chunks cannot be reordered or
  the file truncated without detection.
- The file key is wrapped (encrypted) with the drive key and stored in Postgres
  with the version row. Wrapped keys are ciphertext; the server cannot use them.
- A share link carries only that version's file key in the URL fragment, so
  sharing one file never exposes the drive key or other files.
- Ciphertext starts with a small header (format version, chunk size, base
  nonce) so the format can change later.
- Use only Node's built-in `crypto` / WebCrypto (works in Node and browsers).
  No custom primitives.

## Phases

Each phase ends with a merged PR (or a few), a successful `pnpm verify`, and
the phase's tests added to the local regression suite. Later phases must not
break earlier phases' tests.

### Phase 0 — Repository and regression gate

**Build:** pnpm workspace, TypeScript strict, lint, formatter, Vitest, a
`docker-compose.yml` with Postgres and MinIO, and a GitHub Actions workflow
that retains the checks for manual dispatch only. `pnpm verify` runs lint,
typecheck, unit, integration, MCP, Playwright, and build checks in order.
`.env.example` lists the known variables.

**Test:** `pnpm verify` passes its scaffold smoke tests; `pnpm services:up`
brings up Postgres and MinIO locally and completes bucket initialization.

**Regression:** `pnpm verify` is the required local regression gate for every
later phase. GitHub Actions are opt-in through `workflow_dispatch`; they do
not run automatically on pull requests or pushes.

### Phase 1 — Core API and metadata (S1.3–S1.6, S3.1–S3.8 server side, S5.1–S5.4)

**Build:** database schema (accounts, agents, machines, drives, API keys,
files, versions, audit events); API-key auth middleware with permission
scopes; endpoints for create drive/agent/key, `whoami`, put (returns
presigned upload URL, then commit), get (presigned download URL), list,
move, copy, delete, versions, restore, recent, search by path/tag/author.
Conditional writes by version id. Each version records agent, machine, user.
Audit event on every call.

**Test:**
- Integration tests against real Postgres and MinIO: full put → commit → get
  → overwrite → versions → restore → delete cycle.
- Permission tests: a read-only key cannot write; a key for drive A cannot
  touch drive B; a revoked key fails.
- Conditional write: two writers with the same base version; exactly one wins,
  the other gets a conflict error.
- Error shape tests for not found, permission denied, quota exceeded.

**Regression:** these integration tests stay in `pnpm verify` permanently. Add
an API contract snapshot (OpenAPI or typed route list) so accidental breaking
changes show up in review.

### Phase 2 — Client library, encryption, CLI (S1.3, S2.1–S2.3, S2.5, S3.*, S4.4)

**Build:** encryption module (design above), API client, and CLI commands:
`login`, `drive create` (generates and displays the drive key with a backup
warning), `agent create`, `key create`, `put`, `get`, `ls`, `mv`, `cp`, `rm`,
`versions`, `restore`, `sync`, `whoami`.

**Test:**
- Crypto unit tests: round trip for empty, 1-byte, exactly 1 MiB, multi-chunk,
  and 100 MiB files; wrong key fails; flipped byte fails; reordered chunks
  fail; truncated file fails.
- Fixed test vectors (known key + nonce → known ciphertext) committed to the
  repo so a future change to the format is caught.
- **Plaintext-never-leaves test:** upload a file containing a unique marker
  string, then scan the raw MinIO object and every Postgres row for that
  marker; the test fails if it is found.
- CLI end-to-end against the local stack: create drive, put, get, compare
  bytes; `sync` uploads only changed files on a second run.
- Missing or wrong drive key produces the S2.5 error, not garbage output.

**Regression:** test vectors and the plaintext-never-leaves test are
permanent and must never be edited to make a change pass.

### Phase 3 — MCP server and skill (S1.2, S1.5, S3.*, S4.1–S4.3, S10.2, S11.*)

**Build:** `agent-drive mcp` stdio server exposing `whoami`, `put`, `get`,
`list`, `move`, `copy`, `delete`, `versions`, `restore`, `search`, `recent`,
`share`. Tool results mark file contents as untrusted data. The skill
(`skills/agent-drive/SKILL.md`): when to save and when not to, folder layout
(`/memory`, `/work/<task-id>`, `/outputs`, `/inbox`), handoff file format.
README with `claude mcp add` and Codex config examples.

**Test:**
- MCP integration test using the SDK's client: spawn the server, list tools,
  call each tool against the local stack, assert results.
- Tool schema snapshot test, so tool names and arguments change only on
  purpose.
- Manual live check (once): add the server to Claude Code, ask it to save and
  retrieve a file, confirm in the console.

**Regression:** the MCP integration test and tool schema snapshot stay in
`pnpm verify`.

### Phase 4 — Console and sign-up (S1.1, S8.1–S8.4)

**Build:** Clerk sign-up (with GitHub as an optional Clerk provider), onboarding
that creates a first drive (key generated in the browser) and API key, drive
browser with in-browser decryption, agent and key management (create, revoke),
usage page, version restore and trash.

**Test:**
- Playwright: sign up with the configured auth provider, create drive, save key, upload
  through the CLI, see the file in the console, download and compare bytes,
  revoke a key and confirm the CLI then fails.
- Console without the drive key shows file names but cannot download contents.

**Regression:** the Playwright journey stays in `pnpm verify`.

### Phase 5 — Sharing (S6.1–S6.3)

**Build:** `share` creates an expiring link `/s/<id>#k=<file key>`. Share page
fetches ciphertext through a presigned URL and decrypts in the browser.
Revoke and expiry enforced by the API.

**Test:**
- Playwright: create a link from the CLI, open it in a fresh browser context,
  download, compare bytes.
- Expired and revoked links return a clear error page.
- Assert server request logs for the share page never contain the fragment.
- A share link's key cannot decrypt a different file in the same drive.

**Regression:** sharing tests join `pnpm verify`.

### Phase 6 — Billing and limits (S9.1–S9.6, S10.4)

**Build:** plans and quotas (drives, storage, egress) enforced in the API;
Stripe Checkout and customer portal; metered usage reported to Stripe; spend
caps and alert emails; `payment_required` error with an upgrade URL; per-key
rate limits; per-file size limit.

**Test:**
- Unit tests for quota math (including versions counting toward storage).
- Integration: free account exceeds storage → `payment_required` with upgrade
  link; upgrade via Stripe test mode webhook → write succeeds.
- Spend cap reached → writes blocked, reads still allowed.
- Rate limit returns 429 with retry-after.

**Regression:** quota and billing tests join `pnpm verify`; Stripe webhook
payload fixtures are committed so webhook handling is tested without the network.

### Phase 7 — Hardening and launch (S10.3, docs, deploy)

**Build:** account and drive deletion (all objects and versions); audit log
view; production S3 bucket with public access blocked and TLS-only policy;
Vercel production deployment; README, quickstart, pricing page.

**Test:**
- Deletion test: after deleting a drive, no objects remain under its S3 prefix
  and no metadata rows remain.
- Smoke test script against the deployed preview: sign up path, CLI put/get,
  share link. Run once per release.
- `/code-astra-review` on the final diff before each PR.

**Regression:** the deployed smoke script runs on every production release.

## Regression strategy (summary)

- Before merge, run the full local gate with `pnpm verify`: lint, typecheck,
  unit, integration (Postgres + MinIO), MCP integration, Playwright, and build.
  GitHub Actions are manual opt-in only, not an automatic per-PR gate.
- Permanent guard tests that must never be weakened: crypto test vectors,
  tamper detection, plaintext-never-leaves, cross-drive and revoked-key
  permission checks, share-key isolation.
- Snapshot tests for the API contract and MCP tool schemas catch unintended
  interface changes.
- A bug fix starts with a failing test that reproduces it.
