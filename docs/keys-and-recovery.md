# Keys and recovery

This page lists every key and secret in Agent Drive, says where each one is kept and what it unlocks, and says what happens if you lose it. Read it before you decide where to keep backups. The steps to back up and restore are in [Back up and recover your drive key](backup-and-recovery.md). The byte formats are in [Encryption format](crypto.md).

A lost drive key cannot be recovered by Agent Drive. The service never has it.

## The drive key

A drive key is 32 random bytes, written as 43 characters of base64url. The client that creates the drive generates it. It is never sent to the API or to S3.

Every file version gets its own random file key. The drive key wraps (encrypts) each file key, and the service stores the wrapped keys. Anyone with the drive key can open every file in that drive. Anyone without it can open none.

The CLI looks for the drive key in this order and uses the first one it finds:

1. `AGENT_DRIVE_KEY_<DRIVE_ID>`: the drive ID in uppercase, with each character that is not a letter or digit replaced by `_`.
2. `AGENT_DRIVE_KEY`
3. The file named by `--key-file`
4. The key saved in the config file, `~/.config/agent-drive/config.json` (or the path in `AGENT_DRIVE_CONFIG`)

The config directory has mode `0700` and the file has mode `0600`. The config records which API origin each saved key belongs to. A key saved for another origin, or one that does not decode to 32 bytes, is not used.

A key from an environment variable or `--key-file` is outside the config file. For that reason, `agent-drive check` does not require a backup for it.

Never store a drive key in the drive it unlocks.

## Unlocking drives in the dashboard

Sign in to browse file names, folders, sizes and history. Opening file contents requires the browser to unlock the drive.

- **Recovery file.** A JSON file with `format`, `driveId` and `key`. You download it from the console when you create a drive, or later from the key menu. For a drive added to your account, the dashboard can unlock it as part of the download. You choose it again whenever a tab needs the key. The key stays in that tab. It is cleared when you reload or after 30 minutes without use.
- **Passphrase unlock.** You can set up a passphrase in the console; Files prompts for it until you do. The browser makes an account key pair and wraps its private key with a key derived from the passphrase (PBKDF2-SHA-256, 600,000 iterations by default). When a drive is added to your account, its key is sealed to the account public key and stored as a slot. Typing the passphrase then opens every drive you added. The console can generate a 20-character passphrase for you, which has 100 bits of randomness. A passphrase you choose yourself must be at least 14 characters.
- **Agents seal their drive keys to your account automatically.** An agent that holds a drive key seals it to the account public key on `drive create`, `login`, `credentials import` and MCP server start, and at most once every 24 hours on other commands that load a drive key. `agent-drive account seal` does it on demand. Sealing is best-effort and never fails the agent's own command. For an older drive, an agent that still has the key can run `agent-drive account seal --drive <drive id>` to make it available immediately.
- **First-time sealing verifies the account key.** A machine seals only to an account key you have verified: the first time a machine seals for an API origin, `account seal` needs `--fingerprint <the fingerprint>` — the value shown in the console under Settings — or the fingerprint preset as `AGENT_DRIVE_ACCOUNT_KEY_FINGERPRINT`. The machine pins that fingerprint and refuses any different account key from then on. Without a verified fingerprint nothing is sealed and nothing is pinned: automatic sealing prints one warning instead of failing, and `account seal` reports `unverified`. After a passphrase reset, `account seal --repin --fingerprint <new fingerprint>` pins the new key. This keeps a compromised service from substituting its own account key at first contact and receiving your sealed drive keys.
- **Previously saved account-key pins.** Versions before independent fingerprint verification may have pinned the API's first response automatically. These pins remain on disk but do not authorize sealing after upgrade until the owner verifies the fingerprint once with `--fingerprint`; if the verified key differs from the saved pin, use `--repin --fingerprint`.
- **Keep this browser unlocked** (on by default at the passphrase prompt, and used by setup) keeps the account private key in that browser's IndexedDB as a non-extractable CryptoKey: a handle the browser can use for ECDH but never export, never a string in storage. Later visits open your drives with no prompt. "Lock this browser" in the key menu deletes it, and signing out or a different user in the tab clears it.
- **Passkey unlock.** After passphrase unlock is set up, you can enroll a passkey — a synced passkey or a security key — as a second way to unwrap the same account private key. Enrollment asks for the current passphrase and a strict sign-in check (reverification). The authenticator's WebAuthn PRF output wraps the private key; the service stores the public credential ID, an IV and the wrapped key, never the PRF output. The same passkey then opens your added drives on any browser where it is present, including another device that syncs it. A passkey is another wrapper of the account key, not a backup of any drive key; agent-only drives are unaffected.
- **Agent-only drives** are never sealed to your account. Create one with `agent-drive drive create --name N --agent-only` or the "Agent-only" checkbox on New drive in the console. The console always asks for an agent-only drive's recovery file, and neither the console nor the API adds a passphrase-unlock slot for it.

Slots are not backups. A slot is added when an agent that holds the drive key seals it, or after you load a drive's key from a recovery file or bundle, and adding one does not change the drive's backup status. A slot works while you are signed in and can unlock the account key. Keep a recovery file or a bundle as your backup.

Changing the passphrase re-wraps the same account key. It does not lock out someone who already knows the old passphrase. If the passphrase may be known, reset it instead. A reset deletes the account key and removes every drive from it, and a passkey wrapper goes with it. Files are not deleted. You add each drive again with its recovery file. Anyone who already opened a drive keeps its key.

## What losing each key means

| If you lose                                                          | What happens                                                                                         | How to recover                                                                                                                                                                                            |
| -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The drive key, with no backup anywhere                               | The files in that drive can never be decrypted. Paths, sizes, tags and version history stay visible. | Not possible. Agent Drive cannot recover or reset a drive key.                                                                                                                                            |
| The drive key on one machine, but you have a bundle or recovery file | Nothing is lost.                                                                                     | Import the bundle with `agent-drive credentials import`, or load the recovery file in the console. See [Back up and recover your drive key](backup-and-recovery.md).                                      |
| An API key (the config file or the secret is gone)                   | The agent cannot call the API. Files are not affected.                                               | Revoke the key if it may have leaked, then run `agent-drive login` again. Reconnecting an old drive to a new agent needs the drive key from a recovery file or bundle.                                    |
| The passphrase                                                       | The console cannot open your drives with it.                                                         | Use your enrolled passkey to open your drives and save recovery files before resetting the passphrase. If you have no passkey, use a recovery file or an agent that holds the key. Files are not deleted. |
| A passkey                                                            | Nothing is lost — the passphrase still opens the account.                                            | Unlock with your passphrase and save recovery files. The dashboard supports one enrolled passkey per account key.                                                                                         |
| A recovery file                                                      | Nothing is lost if another copy of the drive key exists.                                             | Download a new one from the console with a key loaded, or export a new bundle with the CLI.                                                                                                               |
| A credentials bundle                                                 | Nothing is lost if the CLI config still exists. The bundle held an API key that may now be exposed.  | Run `agent-drive credentials export` again. Revoke the old API key if the bundle may have leaked.                                                                                                         |
| A share link                                                         | The file is not affected. Whoever has the link can still read that version until it expires.         | Run `agent-drive share list`, then `agent-drive share revoke SHARE_ID`, and make a new link.                                                                                                              |
| A webhook token                                                      | OpenRouter can no longer send traces.                                                                | In the console, replace the token and update OpenRouter.                                                                                                                                                  |

## Rotation and revocation

Revoke an API key when an agent or a machine is no longer trusted:

```sh
agent-drive key revoke <key id>
```

You can also revoke an agent or a key in the console. A key that an agent issued with `agent-drive credentials issue` can be revoked alone, from the console under Agents. Revoking the key of the agent that issued it does not revoke the keys it issued.

Revoke a share link with `agent-drive share revoke SHARE_ID`. Replace or revoke a webhook token in the console. The service checks API keys and webhook tokens for revocation on every request.

What revoking does not do:

- It does not change the drive key. A person or machine that already has the drive key can still decrypt any ciphertext it has, and any ciphertext it can still obtain by other means.
- It does not re-encrypt past data.
- Revoking an API key does not remove a copy of the key from a backup bundle. The bundle's API key stops working, but the drive key in it stays valid.

Agent Drive has no command or console action that rotates a drive key. [Encryption format](crypto.md) says a future rotation format has to be versioned. To move to a new drive key today, create a new drive, download each file from the old drive with `agent-drive get --output` and upload it to the new drive with `agent-drive put`, then delete the old drive. Deleting is queued, not immediate. See [Threat model](threat-model.md).
