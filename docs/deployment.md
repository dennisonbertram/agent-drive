# Deployment, maintenance, and release gates

This is an operator runbook, not evidence that a hosted environment has been deployed or tested.
Use a dedicated Agent Drive Clerk instance, database, object buckets, Vercel project, and billing
configuration. Never borrow another application's credentials. No GitHub Actions are required.

## Private storage

`infra/storage.cfn.json` provisions two retained S3 buckets and a scoped managed IAM policy.
Review it and validate it with AWS CloudFormation before deploying into the chosen AWS account.
Supply globally unique `DataBucketName` and `LogsBucketName`, the exact HTTPS `PublicOrigin`
(no trailing slash), and the desired `LogRetentionDays` (default 90).

Both buckets block all public access, disable ACL ownership, use SSE-S3, and deny insecure
non-service requests. The log-delivery service has a separate account/source-bucket-restricted
permission. Data CORS permits only the configured origin and GET/HEAD/PUT. Add an explicitly
approved candidate origin when testing a separate preview; do not use wildcard CORS.

Attach the output managed policy only to a dedicated runtime/maintenance principal. It permits
application-prefix object access, permanent version deletion, and log-prefix reads—not bucket
administration. Prefer short-lived workload credentials. No access keys are generated by the template.
Configure `S3_BUCKET`, `S3_REGION`, `S3_LOGS_BUCKET`, and `S3_LOGS_PREFIX=access/` from its outputs.
Leave `S3_ENDPOINT` unset for AWS; never carry a local MinIO endpoint or credentials into production.

S3 versioning is intentionally not enabled: application versions already use immutable distinct
object keys. Enabling bucket versioning silently retains additional physical bytes outside the
logical billing ledger. Cleanup handles versions/delete markers defensively if versioning was
previously enabled. Lifecycle expires only `staging/` bytes and abandoned multipart uploads;
it never expires committed `objects/` data. Bucket retention protects against accidental stack
deletion; deleting a CloudFormation stack is not an account-erasure procedure.

Server access logs are delayed/best-effort and contain operational metadata. Keep them private;
their retention is independent of account deletion. Verify actual log arrival and egress ingestion
before enabling paid checkout. Static policy tests do not prove the deployed bucket's configuration.

## Vercel and authentication

Create/link a dedicated Vercel project with repository root directory `apps/web`, Node 24,
and the included `apps/web/vercel.json`. Its build commands install the root workspace and build
the CLI library before Next.js. Enable access to source outside the root directory if required
by the project's monorepo settings. Link the CLI from the repository root, keeping `.vercel/`
out of version control. Review the resulting project ID before deploying.

Configure a production PostgreSQL connection with TLS/pooling appropriate for serverless traffic,
then apply the checked-in migrations using `pnpm --filter @agent-drive/web db:migrate` from a
trusted operator environment. Back up and review migrations first; builds do not run migrations.

Add dedicated Clerk publishable/secret keys, storage configuration, and `AGENT_DRIVE_PUBLIC_URL`
as a trusted HTTPS origin to the Vercel environment. Configure Clerk redirect/origin/provider
settings for each domain being tested. Never set `AGENT_DRIVE_TEST_AUTH` in a hosted deployment.
Use separate preview resources when testing migration/provider changes against nonproduction data.

Configure Stripe and optional email only as described in the README. Synthetic signatures and
mocked providers do not establish live payments, email delivery, or final-invoice correctness.

## Maintenance is required

On Vercel Pro, the checked-in cron schedules run these maintenance jobs through
`/api/cron/maintenance`. Configure `CRON_SECRET` in the Vercel Production environment with at least
32 random characters. The CLI commands remain available for a trusted external worker with the same
database/storage/provider configuration:

```sh
pnpm --filter @agent-drive/web deletion:maintenance
pnpm --filter @agent-drive/web maintenance:cleanup-expired-uploads
pnpm --filter @agent-drive/web billing:run
```

Run deletion/upload cleanup frequently (for example, every five minutes), and billing at least
hourly. Each pass is bounded; monitor pending/blocked jobs and increase execution frequency when
there is a backlog. A web deployment without the Vercel Pro cron schedules or an external worker
does not run the maintenance jobs.

Deletion first denies new application access, waits at least the presigned-upload grace period,
then purges objects and metadata. Direct S3 links/in-flight requests cannot be recalled instantly.
Repeated prefix sweeps and staging lifecycle rules remove late uploads. Minimal deletion IDs
and hashed revoked identity records remain for cleanup and stale-session protection.

Account deletion settles known usage, drains pending metering, closes open Checkout Sessions,
and cancels subscriptions before final metadata removal. Ambiguous Checkout/meter delivery or
provider failures require retry/reconciliation, not a false success. External invoices, provider
records, backups, and access logs have separate retention. Delayed storage logs mean a final
invoice cannot be promised to contain every late transfer. Never manually drop a blocked job
or its billing rows merely to make the console show completion.

## Every production release

Automatic Vercel Git deployments are disabled in the checked-in configuration, so a merge does
not promote an untested build. After linking the dedicated project and installing/authenticating
an approved Vercel CLI, use the repository's release entry point:

```sh
pnpm release --production-url https://YOUR-PRODUCTION-ORIGIN
```

It runs `pnpm verify`, creates a staged production build using `vercel deploy --prod --skip-domain`,
runs deployed smoke acceptance, promotes only on success, then repeats smoke on the production
origin. No GitHub Actions are invoked. Do not bypass this command with a direct production deploy.
The release checks must run on a workstation with local test services and a Playwright browser.
They are interactive: complete signup with a NEW disposable identity when the browser opens.
The smoke requires an observed completed Clerk signup, not just a successful HTML response.

The candidate must be reachable by its browser AND the CLI, and Clerk/CORS must allow its origin.
Deployment protection that requires interactive Vercel login prevents CLI smoke and therefore
blocks promotion; arrange approved candidate access rather than disabling organization-wide
protection or claiming the test passed. Production-environment staging may use production resources:
only synthetic payloads and a disposable isolated workspace are created.

To run smoke independently against a deployed preview:

```sh
pnpm smoke:release --url https://YOUR-CANDIDATE-ORIGIN
```

It signs up, provisions through the console, performs encrypted CLI put/get with byte equality,
downloads an anonymous encrypted share, verifies fragment secrecy, and revokes the share.
It revokes the created agent's keys and requests deletion of its drive in a finally block.
Reports contain no tokens, drive keys, plaintext payloads, or share fragments. Temporary files
and browser contexts are removed. The disposable identity/revoked agent metadata remain: delete
that test account when finished. Drive cleanup is asynchronous and must be monitored separately.

Local regression of the same script is available with `--local-test-auth --headless`, a loopback
`--url`, and `AGENT_DRIVE_SMOKE_TEST_AUTH_SECRET` supplied securely for the running development
server. This mode is explicitly labeled synthetic and cannot satisfy hosted signup acceptance.
The same local smoke is a permanent Playwright regression. Local mode also queues deletion of its
new synthetic account; the maintenance worker must finish that asynchronous purge.

Account deletion retains only aggregate billing receipts (plan, periods, numeric usage and amounts,
and rate snapshots), opaque deletion-control IDs, and hashed identity tombstones locally. Receipts
exclude agent/file names, paths, credentials, email addresses, and external identity/customer IDs.
Payment-provider records and private access logs follow their separately configured retention.

Store the sanitized reports under `test-results/release-*/` with the release record. A candidate
failure prevents promotion. A post-promotion failure exits nonzero but cannot undo the already
promoted deployment: inspect it and restore the known-good deployment using Vercel's approved
rollback process. Never bypass security/merge gates or erase a failed report.
