# C06: First-run console and key backup

Review note: external MUSE Wonder and Gemini Argon judges were skipped in this run. Scores come from the three internal lenses only.

## Problem

The first visit offers competing "create a drive" paths, and the backup banner does not reflect a saved recovery file. Root cause confirmed in code: the receipt's "Save recovery key" (console.tsx ~1330) saves the file but never POSTs `drives/{id}/key-backup`; only `downloadRecoveryFile()` (line ~495) does. Findings: F16, F19, the drive-name field with no default, walker F-024-01, ux-flow proposal 3. F19 was seen in a headless browser, so a real-browser check is needed. Acceptance criteria are C06 items 1 to 6 in `problems.md`.

## Options considered

| Option                        | Idea                                                         | Score (U / V / E) |
| ----------------------------- | ------------------------------------------------------------ | ----------------- |
| A Fix backup call + reorder   | One shared helper, one receipt button, reordered first run   | 53 / 51 / 52      |
| B Inline checklist, no dialog | Remove the receipt modal                                     | 42 / 48 / 42      |
| C Checklist + recovery kit    | Checklist with text link for "create a drive" and hidden key | 51 / 52 / 51      |

## Decision

Option A, with grafts from C.

1. A single helper does the backup: download the recovery file and POST `drives/{id}/key-backup` with body `{ method: 'file' }`. The banner action and the receipt both call it.
2. Receipt dialog has one button, "Download recovery file and continue": it downloads, POSTs key-backup, refreshes the drive list and closes. No checkbox. The plaintext key is hidden behind a `<details>` (graft from C). The dialog says: "Without it nobody, including us, can open this drive." and shows "Step 1 of 3".
3. The key chip from C05 replaces the old banner: no separate "Key backed up" banner exists. After the helper succeeds the chip menu reads "Key backed up" (green, `--ok`), never "hasn't been backed up". The toast reads "Recovery file downloaded. Store it in a password manager." ("backed up" means the download started; we cannot confirm the file was saved).
4. The New drive name field defaults to "my-drive" when there are no drives and submits with Enter.
5. First-run panel: leads with "Connect your agent" (llms.txt line and an orange Copy button); "New drive" is secondary (no "↗" on in-page actions). The panel is vertically balanced with min-height 60vh so it fills at least 35% of the 1440x900 viewport.
6. Step list uses numerals like the landing page; states (done, current) are derived from data (drive exists, agent connected, `key_backup_at` set), so "Back up your key" stays current until backup is recorded.

## Why this is the best

- Against B: removing the non-closable receipt makes the drive key exist only in page state; closing the tab before backup loses the only copy and the drive can never be opened. The dialog is the guard. It is also an M-L rewrite with rewritten e2e tests.
- Against C: C hides "create a drive" as a text link that a user who only wants a drive may miss; A keeps a visible secondary button. C's wording, Step line and hidden plaintext key are taken.
- Norms satisfied: one primary per screen, one confirmation instead of checkbox gating, honest copy, state derived from data not local flags.
- Costs: password-manager users need one click to open the `<details>` to copy the key. Needs a real-browser check of the F19 fix.
- Rules out: inline checklist without the receipt, a persistent "Key backed up" banner.

## Final acceptance criteria

`problems.md` C06 items 1 to 6, amended: item 4 is satisfied by the C05 chip ("Key backed up", green) instead of a banner.
