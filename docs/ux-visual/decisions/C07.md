# C07: /connect: approval card, existing-drive form, approved next step

Review note: external MUSE Wonder and Gemini Argon judges were skipped in this run. Scores come from the three internal lenses only.

## Problem

The review card stacks equal blocks, so the pairing code outranks the decision, the delegate option precedes Approve, the existing-drive branch is a hidden link that expands the card to 1,300 px (Approve at y about 1155), and the approved state has no onward link. Findings: CN-1 to CN-17 and A-4; folds ux-flow proposal 7. Acceptance criteria are C07 items 1 to 11 in `problems.md`.

## Options considered

| Option                      | Idea                                           | Score (U / V / E) |
| --------------------------- | ---------------------------------------------- | ----------------- |
| A Reorder + shrink          | Reorder inside `connect.tsx`, no new component | 47 / 53 / 52      |
| B Decision card, sticky bar | Radio cards, sticky footer                     | 50 / 48 / 44      |
| C OAuth consent layout      | Heading, bullet list, Deny/Approve             | 51 / 50 / 48      |

## Decision

Option A with C's ordering and B's sticky footer at 390.

1. Order top to bottom: decision heading ("Connect vis-agent-a?", the largest text); permissions as a plain capability list (drive, access, write paths); the pairing code line directly above Approve ("Does this code match your terminal?"); Approve. The code is smaller than the heading. Security reason: the code check must come before the approving action.
2. The delegate option sits behind a closed disclosure.
3. "Add to an existing drive" is a visible secondary button (at least 40 px tall) that opens an inline step. That step keeps Approve in view: at 390 a sticky footer holds Approve; at 1440 the card is at most 850 px high.
4. Checkboxes use the design system's styled control, 24 px or larger hit area (44 px rows); hint text at least 16 px from Approve; labels 4 to 8 px above their field and at least 16 px below the previous one; the file input is styled like other controls; the secret has the same name as the console (one word, per C10).
5. Field errors appear next to the field, highlight it, scroll into view, and replace raw browser messages. The unknown-code banner uses the error treatment and inserts with 0 px shift.
6. Code field focuses on load, uppercases input and inserts the hyphen.
7. Poll `device/<code>` every 5 s while waiting for a later offer before approval, stop after 10 minutes; the existing 409 fallback stays.
8. Approved state names what was granted, links to the console, says the console will update, and does not repeat "Approved" in heading and body.
9. Brand mark placed the same as on /sign-in (same left alignment and top offset).
10. Account chip, if shown, uses the account name or email, not "workspace".
11. NO Deny button. The owner explicitly decided earlier to remove Deny from /connect. Judges for C and B proposed Deny (and the usability judge cited its absence in A as a weakness); that is overruled by the owner's prior decision, and the engineering judge also noted it is new behaviour beyond the criteria. A user who does not recognise the code leaves the page without approving.

## Why this is the best

- Against B: sticky footer in a scrolling card has a keyboard-open risk on phones; radio cards and a segmented control are new patterns; its heading repeats "workspace". The sticky footer idea is used only at 390.
- Against C: depends on a Deny button the owner removed, and needs a sub-view state; its consent layout ordering is adopted.
- Norms satisfied: decision outranks supporting data, anti-phishing code check before the action, progressive disclosure for rare options, errors beside fields, 44 px touch rows.
- Costs: the polling needs a fake-timer test; wording changes must ship with C10 or the surfaces disagree; the sticky footer at 390 needs a keyboard-open check.
- Rules out: Deny on /connect, radio cards, inline permanent expansion of the existing-drive form.

## Final acceptance criteria

`problems.md` C07 items 1 to 11, with the heading, order and no-Deny rules above.

## Test plan

- Playwright at 1440x900, 768x1024 and 390x844: Approve inside the viewport in review-new and offer; existing-drive form at 1440 inside the viewport, at 390 reachable within a 300 px scroll; heading font size greater than code font size; code line directly above Approve in DOM order; no Deny button exists.
- Inline error next to its field and scrolled into view; unknown-code banner shifts the field by 0 px.
- Fake-timer test for 5 s polling and the 10-minute stop.
