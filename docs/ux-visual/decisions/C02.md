# C02: Console error, loading and empty states

Review note: external MUSE Wonder and Gemini Argon judges were skipped in this run. Scores come from the three internal lenses only.

## Problem
The console has no shared list-state components. Each tab renders a raw string for errors ("Failed to fetch"), has its own empty copy, and nothing keys the empty state to a failed load, so an error shows above a false "Ready for your first file". The error banner shifts content 56 px. A filter with few matches leaves dead space. Trash columns truncate or repeat one value. Findings: F05, F10, F08, part of F18, and the unverified loading state. Acceptance criteria are C02 items 1 to 6 in `problems.md`.

## Options considered
| Option | Idea | Score (U / V / E) |
|---|---|---|
| A Inline StateBlock | Fix Files and Trash with condition ordering and a state block | 43 / 43 / 45 |
| B ListState + useListLoad | Shared `<ListState>` component and one status value per list | 52 / 52 / 54 |
| C Convention | Dropbox-style: remove footer, dimmed stale rows with error bar | 40 / 38 / 38 |

## Decision
Option B, landing first in the build order, with grafts.
1. A `useListLoad` hook returns one status value per list: `loading | slow | error | ready`. `slow` is set after 10 s. A single value cannot be both error and empty, so the false empty state is impossible.
2. A shared `<ListState>` component renders skeleton rows (loading), "Still loading" with Retry (slow), a plain-language message with Retry using `--danger` colour and `role=alert` (error), and the empty and zero-match variants (ready). A skeleton appears within 150 ms of the request.
3. Ship Files and Trash in the first PR. Agents, API keys and Usage adopt `<ListState>` after C04 settles, to limit conflicts in `console.tsx`.
4. Graft from A: `friendlyError()` maps "Failed to fetch" and similar to "Could not load files" (and the equivalent per list), and the panel gets a reserved `min-height` so changing state moves nothing more than 2 px.
5. Zero matches: "No files match 'x'" with a Clear filter button. A filter with one match leaves no more than 24 px below the footer.
6. Keep the footer line "File contents encrypted / Paths and metadata visible to the service". Do not remove it.
7. Trash columns: Name, Deleted (full date, no wrap), Size. File count appears at most twice on the Files screen.
8. The skeleton uses the table column template exposed as a CSS variable, so C04's column changes carry through; where that is not possible, generic bars.
9. Define `--danger` once in `globals.css` (shared with C03 and C05; documented under C05).

## Why this is the best
- Against A: A fixes only Files and Trash and leaves three tabs hand-rolled; loading remains a text block, not a skeleton. B fixes the cause (one status value) instead of the ordering of conditions.
- Against C: removing the footer drops a privacy disclosure, which is a product decision rather than a UX tweak; keeping stale rows under an error bar adds a state users must interpret and tests must cover.
- Norms satisfied: consistent states across every list, no layout shift, plain language errors, visible system status.
- Costs: B edits five tabs in a 1,580-line file that C03 and C04 also edit, hence it lands first. Moderate effort.
- Rules out: per-tab error copy, stale rows shown beneath an error, removing the footer.

## Final acceptance criteria
`problems.md` C02 items 1 to 6, with the additions above (footer kept, Trash columns Name / Deleted / Size).

## Test plan
- Unit test for `useListLoad` with fake timers: loading, slow at 10 s, error, ready, retry.
- Playwright: a failed list shows the message, Retry and role=alert and never "Ready for your first file"; swapping loading to error moves no element more than 2 px; zero-match filter shows the message and Clear filter; Trash date not truncated at 1440 and 768; no column in Trash holds one value in every row.
- Failing first: the error-then-empty assertion.
