# C08: Share from the console: Share action and Shared links list

Review note: external MUSE Wonder and Gemini Argon judges were skipped in this run. Scores come from the three internal lenses only.

## Problem
Sharing exists in the CLI and API but the console has no Share action or list, so a human sender cannot do the job (0 of 3 steps). No inspector screenshot exists for an absent screen; evidence is ux-flow proposal 5, walker F-STORY-046-01 and the code (no share handler in `console.tsx`). Acceptance criteria are C08 items 1 to 5 in `problems.md`.

## Options considered
| Option | Idea | Score (U / V / E) |
|---|---|---|
| A Share action + 2 dialogs | Share dialog plus a Shared links list | 51 / 51 / 53 |
| B Shared filter + chip | Shared filter, per-row chip | 48 / 48 / 44 |
| C Share dialog + Shared page | Sixth nav item | 42 / 41 / 40 |

## Decision
Option A with grafts.
1. Feasibility is confirmed: the CLI's `createShare` does a metadata GET, `unwrapFileKey(wrappedKey, driveKey)`, then POSTs `{path, versionId, expiresAt}` and builds `/s/<id>#k=<fileKey>`. The console already holds the drive key and has the `share` scope. The file key exists only in page memory and the URL fragment (never sent to the server).
2. Share is an item in C03's "⋯" menu and also a visible row action beside Download on wide screens.
3. The Share dialog has expiry 1 h / 24 h / 7 d / 30 d (default 7 d) and one orange "Copy link". The full URL including `#k=` is copied and a toast says "Link copied". With no key loaded, the C05 unlock prompt opens first (`pendingAction`).
4. The dialog contains "Links for this file" (created, expires, status) with inline two-step Revoke (no nested dialog). The row updates in place.
5. A "Shared" view in C04's switcher lists all links: file, created, expires, status, Revoke.
6. Help text once: "A link can only be copied when it is created." (the server stores no key; the list API returns no URL).
7. Copy uses the ClipboardItem promise form for Safari. If the clipboard write fails, the in-memory URL is reused on the retry; a second click never creates a duplicate share. The URL is never written to localStorage, logs, analytics or the query string.
8. Trash: the share count per file is loaded in the background, so the Trash toast stays under 100 ms. Confirm before Trash only when the file has active links, naming the count: "N share links stop working; restoring the file turns them back on."

## Why this is the best
- Against B: per-row chips need every share loaded when Files opens (an extra paged request) and two lists to keep in sync; the "Links for this file" graft gives the same revoke-where-created benefit.
- Against C: a sixth nav item works against the plan to reduce tabs and costs the most.
- Norms satisfied: sharing where the file is, 2 clicks from the row, honest limits stated, security of the zero-knowledge model preserved.
- Costs: depends on C03 (menu, Toast, ConfirmDialog), C04 (view switcher) and C05 (unlock prompt). Old links cannot be re-copied.
- Rules out: a separate Shared page, row chips, storing share URLs.

## Final acceptance criteria
`problems.md` C08 items 1 to 5, with expiry options 1 h/24 h/7 d/30 d, the "Shared" view, the creation-time-only note, and the retry-reuse behaviour.

## Test plan
- Failing first: Share exists in the row menu and the dialog creates a link in at most 3 clicks.
- The share POST body carries no key (only path, versionId, expiresAt); the copied URL has `#k=` with the 43-character key.
- Retried copy after a clipboard failure creates exactly one share.
- Revoke updates in place; Trash confirm appears only when active links exist; sharing with no key opens the unlock prompt.
