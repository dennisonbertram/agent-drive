# K2: The phone page is 13.7 screens and repeats itself

Review note: one judge panel scored all three lenses (usability, visual craft, engineering). External MUSE Wonder and Gemini Argon judges were not run.

## Problem

Desktop multi-column sections stack unchanged on phones, and some facts appear two or three times. At 390x844 the page is 11,555 px (13.7 screens, measured). Problem (1,275), relay (1,916), pricing (1,313) and footer (1,168) take nearly half of it. Findings H-02, H-07, H-08, H-09, H-10, H-15, H-16, H-19.

Original acceptance criteria: page ≤ 9 screens at 390 (≤ 7,600 px); activity log rows labelled on phones; relay stacks below 1000 px; console image readable (≥ 11 px text) at 768; each fact stated once.

B and C reach the height number by putting content behind swipes and tabs. On B, a reader who does not swipe never sees the protein section (the owner's Fable 6.2 message) or two of the three problem scenarios. On C, the same is true behind tabs, and four tab sets are a new interaction this site does not use anywhere else. The page is shorter, but a reader who wants the same information pays for it in taps instead of scrolling, and the protein figure (one of the three figures the owner chose) is hidden by default. B also shrinks the figures to 300 to 330 px inside cards, below the width where H-14 found collisions, which conflicts with K1.

## Decision

Option A, with three grafts from B, one from C, and a revised height target that the owner must accept (see "Owner question").

All selectors are in `apps/web/app/styles/landing.css` unless named otherwise. "Phone" means `max-width: 760px`, the existing landing breakpoint.

1. **Rhythm (phone)**: `.landing section` top padding 48 px (B's value, on the 8 scale; A proposed 56), `.landing h2` 32 px, `.landing .l-final h2` 32 px. `.landing .l-final { padding-bottom: 64px }` and `.landing .site-footer { margin-top: 0 }` at all widths (H-15: removes the 184 px band).
2. **Problem (phone)**: A's change 2. Each scenario stays a horizontal three-box strip with short horizontal arrows (`.l-strip`, `.l-cell`, `.l-arr`). No tabs, no swipe.
3. **Relay**: stack `.l-line3.relay` to one column at `max-width: 1000px` (H-09). On phones, commands keep one line and scroll inside their grey block: `.l-line3 code { white-space: pre; overflow-x: auto; overflow-wrap: normal }`.
4. **Relay jump bullets (phone only)**: add `className="l-jump"` to the "Game development" and "Protein research" items in `ul.l-also` (`page.tsx`) and hide `.l-jump` on phones. They stay on desktop. A class, not `:nth-child`, so reordering the list cannot hide the wrong item.
5. **Graft from B, activity log**: `Log` in `page.tsx` becomes a real `<table className="lt">` at all widths, with header cells "Saved by", "From", "When", and on phones each entry's path in its own row (`<th scope="row" colspan="3">`) above its three values. Remove `role="img"`. Override the global phone rule (`globals.css` line 635, `table { min-width: 620px }`) and the nowrap header rule with `.landing .lt { min-width: 0 }` and `.landing .lt th { white-space: normal }`. This fixes both halves of H-07 (visual labels and screen readers); A's `::before` labels fixed only the visual half.
6. **Pills (H-08)**: in `ul.l-solve` delete the two items that repeat the caption and the FAQ ("Every version kept, with who wrote it", "Per-agent keys and folder limits"). Style the remaining two ("Many agents, one drive", "No silent overwrites") as a plain square-bullet list with no border, at all widths.
7. **Console**: `<source media="(max-width: 1000px)" srcSet="/console-files-phone.png" />` in `page.tsx`, and `.l-shot { max-width: 520px }` between 761 and 1000 px (H-10). Do **not** crop the phone image (B and C proposed a crop): the crop removes the line "File contents encrypted · Paths and metadata visible to the service", which is a disclosure, not decoration.
8. **Features (phone)**: hide the three column tags (`#features .feat > div > .l-tag`) on phones, because the h2 "Encrypted. Sharable. Works anywhere." already names them and the paragraphs follow in the same order. The owner's h2 stays. Desktop keeps the column tags as spec-sheet labels.
9. **Graft from B, compare**: each comparison becomes one block link (`<Link className="cmp-row">` wrapping the tag and summary, with a trailing arrow), and "All comparisons" becomes the last row in the same style. Three columns at 761 px and up, full-width rows on phones; one markup for both. The separate "Agent Drive vs …" link line goes away, so there is one link style for this role (also closes H-11 for K4).
10. **Graft from B, pricing**: `#pricing` becomes a comparison table (`.pt`) built from `PLANS` and `allowance()`: plans as columns (Free; Developer and Team with "Coming soon" under the name), rows for price, drives, stored, downloads per month, API operations per month (1M / 10M / 100M via `Intl.NumberFormat` compact notation), and one full-width filled "Sign up free" below (label and fill owned by K3). Same `.landing .pt { min-width: 0 }` override. When paid checkout is on, the "Coming soon" cells become "Choose plan" links. Full numbers stay on `/pricing`. The table is used at all widths (H-19).
11. **Footer on `/`**: A's change 11, scoped under `.landing` in `landing.css` (only `/` has `main.landing`): hide `.sf-tagline` and `.sf-cta`, hide `.sf-cols nav[aria-label=Compare]` (the compare section links the same pages), brand and GitHub icon in one row, Product and Resources as two columns, link rows 44 px tall. Other pages keep the full footer. No `<details>` collapse (C): with K3's sticky header the footer is secondary, and `<details>` would need a separate desktop branch.

## Why this is the best

- **Against A as proposed**: A is the right base, but it leaves the log as `role="img"` (screen readers still get one label, not a table), keeps pricing as three blocks that cannot be compared at a glance, keeps two link styles in compare, and hides list items with `:nth-child`. The grafts fix each of these and save about 450 px more.
- **Against B**: the swipe rows are the only reason B reaches 7,000 px. They hide the protein figure and the owner's protein message behind a swipe, give two figures 300 to 330 px cards (conflicts with K1), and add a horizontal-scroll pattern to a page that otherwise reads top to bottom. B's tables and compare rows are good and are taken.
- **Against C**: four tab sets plus a new client `Tabs` component is the most code and the most interaction for the reader. The first problem scenario, the first relay step, the game use case and the Free plan are all a reader sees without tapping. Ponytail principle: tabs only if they clearly win, and here they trade scroll for taps without reducing what a reader has to do.
- **Norms satisfied**: D2 and D5 (dead band and repeated chrome removed), L6 (relay reflows at 768), C2 (duplicate pills, jump bullets, footer tagline, CTA and compare column removed on phones), C3 and A2 (log is a labelled table), D1 (console readable at 768), I5 (pricing comparable at once).
- **Costs and what it rules out**: the page stays about 670 px above the original 7,600 px target. Two pills are deleted at all widths (owner copy). Horizontally scrolling commands hide the end of each command until the reader swipes inside the block. Rules out swipe rows, tab sets, the console crop and a collapsed footer for this round.

## Owner question

The original target (≤ 7,600 px) can only be reached by hiding content behind swipes or tabs. **Recommendation: accept a revised target of ≤ 8,300 px at 390 (about 9.8 screens, a 28 percent cut) with every section and all three figures visible without a tap.** If the owner wants the shorter page, the least harmful extra step is B's use-case swipe row (about 600 px saved), at the cost of the protein section being one swipe away.

Copy removed by this decision, for the owner to confirm: the pills "Every version kept, with who wrote it" and "Per-agent keys and folder limits" (all widths), the two "See how" relay bullets (phones only), the features column tags (phones only), the footer tagline, sign-up link and Compare column (homepage only).

## Final acceptance criteria

1. At 390x844, `document.documentElement.scrollHeight` ≤ 8,300 px, with no section using horizontal scroll-snap, tabs or `hidden` panels.
2. The activity log is a `<table>` with column headers "Saved by", "From", "When"; at 390 and 360 every value sits under its header; no `role="img"` on it.
3. At 768x1024 the three relay steps share one left edge (one column), and no command breaks inside a path or flag.
4. At 768x1024 the console `<img>` `currentSrc` ends in `console-files-phone.png` and its rendered width is at most 520 px.
5. No horizontal page overflow at 360, 390, 768 and 1440 (scroll inside code blocks is allowed).
6. On `/` at 390: `ul.l-solve` has two items; the footer shows no visible `/compare/` links, tagline or sign-up link; the compare section has one link per comparison plus "All comparisons", all in one style.
7. Pricing at 390 shows all three plans' price, drives, stored, downloads and API operations in one table, with one "Sign up free" button.
8. Gap between the final CTA's last element and the footer's top rule is 64 px or less.
