Method: lead list from `docs/ux-paths/catalog-setup.md` sections 7 and 8 (written from code, so "suspected" until a walk confirms), cross-checked against `docs/ux-walker/setup-nov27/results.json` (observed in a browser/CLI) and screenshots under `docs/ux-walker/setup-nov27/stories/*/screenshots/`. Screenshots opened: SETUP-003 step-3-onboarding, SETUP-013 step-1, SETUP-035 step-2 and step-7, SETUP-044 step-2, SETUP-059 step-1. Rating key per item: deliberate (accelerator of one canonical route), drift (parallel implementation or wording that diverged), or unclear.

## Duplicate Paths (6 items)

1. **Start agent setup: many entry points, one instruction. Verdict: deliberate, already about right.** Landing hero, closing section, console onboarding, Connect dialog and quickstart all carry the same `Set up Agent Drive: <origin>/llms.txt` line (catalog 7.1/7.2). The console onboarding screenshot (`stories/SETUP-003/screenshots/step-3-onboarding.png`) shows one dominant line with one orange Copy. These are placements of one canonical route, not parallel routes. Keep. The real defect is not the number of entries but that the copies differ (see Duplicate Information 1 and Naming 1), and that the Connect dialog's Copy is invisible (F-SETUP-004-1, `stories/SETUP-004/screenshots/step-5-connect-dialog.png`), which breaks the shortcut.
2. **Create the first drive: agent at `login` vs console `New drive`. Verdict: deliberate but the human-first branch is a dead end (observed).** The onboarding screenshot offers "Prefer to set up a drive yourself? [New drive]". SETUP-015 (status fail): the recovery file that branch produces cannot be imported by the CLI (`credentials import --from agent-drive-<id>.key.json` fails with "Not a valid Agent Drive credentials bundle."). The two routes produce incompatible artifacts. Either make the human-first branch finish (CLI accepts the recovery file) or demote it.
3. **Give a second agent access: five routes. Verdict: drift (observed friction in each).** `grant --verify`, `credentials issue`, recovery file on `/connect`, re-run `login`, manual API key + `login --token-stdin` (catalog 7.1). Walker: manual path is "About 19 actions" (SETUP-047) against a working `grant --verify` (SETUP-043). Manual API key gives no drive key (catalog). See Overlapping Features 1 for the recommended collapse.
4. **Record a backup: 1Password, clipboard, file, `--stdout` plus `confirm`, console Download recovery file. Verdict: drift (observed).** The `check` refusal lists three routes "with no recommended default" (SETUP-027-F2). Two separate records of "backed up" exist and disagree: console says "Key backed up 11/27/2026 (env)" while the laptop CLI says "drive key not backed up" (F-044-05); after saving the console recovery file the CLI still says not backed up (F-SETUP-034-01).
5. **Open a drive in the browser: passphrase, passkey, recovery file, pasted key, `adcred1.` bundle, account seal.** See Overlapping Features 3. Verdict: unclear; the key chip menu in `stories/SETUP-035/screenshots/step-7.png` shows the cost: seven same-weight buttons (Load key, Download recovery file again, Lock, Lock this browser, Add a passkey, Change passphrase, Forgot or exposed passphrase?).
6. **Install the skill (`skill install`, `npx skills add`, copy by hand) and capture traces (toolbar `Capture...`, drive menu `Capture traces...`).** Skill: catalog contradiction 29 says the two routes install to different places with no guidance (Catalog). Capture: two entry points to the same dialog is a fine accelerator; the naming is the problem (Naming 5).

Already minimal: sign-up entry points (header, hero, pricing, footer, sign-in line). Duplicate placements but all go to `/sign-up`; PROD-02 and SETUP-002 observed "Start with Free goes to /sign-up". Only nit: "Sign up free" appears five times on the landing page (F-SETUP-007-1) and the sign-up page repeats the sign-in link three times (F-PROD-01-11). Low value, leave.

Already minimal: reaching the approval page. Printed link, `--no-browser`, and bare `/connect` with an 8-letter code all worked (SETUP-016, SETUP-017). Three routes converge on one screen. Leave.

## Duplicate Information (6 items)

1. **Approval step described three ways (observed, high repeat count).** Landing hero: "Your agent shows a pairing code, and you approve it in your account." Console onboarding: "The agent shows a pairing code. You approve it once." (screenshot `SETUP-003/.../step-3-onboarding.png`: "Paste this line into your agent... open it and click Approve."). Quickstart: "check that the code matches... and click Approve". The real page (`SETUP-013/screenshots/step-1.png`) requires typing a 16-hex "VERIFICATION CODE" and the button reads "Approve agent". Walkers filed this seven times independently (F-SETUP-003-1, F-009-1, F-014-1, F-SETUP-018-01, F-015-7, F-PROD-01-2, catalog contradictions 1, 51, 52). Fix is one sentence: "...then type the verification code from your terminal" in all copies, and generate those copies from one string (suspected cause: copies hand-written in `home.ts`, `console.tsx`, `quickstart.md`).
2. **Two codes on one approval card, both asked about (observed).** The card shows the 8-letter code NTKN-JFWN under "Does this code match your terminal?" and also asks for a typed VERIFICATION CODE (`SETUP-013/step-1.png`). F-013-3: the 8-letter question comes first although the typed 16-hex code is the check that matters. The page says "This page never shows it" in small text. The user must work out which of two codes is the match and which is the secret. Suspected: showing the match question as a one-line confirmation under the input, with the typed code as the single labelled step, would remove the ambiguity.
3. **Backup state kept in two records (observed).** Console `key_backup_at` and CLI config record disagree (F-044-05, F-SETUP-034-01, catalog contradiction 50). Also the console chip text "Key backed up 11/27/2026 (file)" in `SETUP-035/step-7.png` shows a raw method token; with 1Password/`confirm` it shows "(stdout)" and with sandbox bundles "(env)" (F-044-05, contradiction 25). One source of truth, human labels.
4. **Passphrase prompt shown before there is anything to protect (observed).** A brand-new account's Files header reads "Set a passphrase and agents will add every drive's key to your account — then each one opens here automatically. Set up" directly above "Give your first agent a home." (`SETUP-003/step-3-onboarding.png`). F-SETUP-003-2 and SETUP-032-F1 describe it competing with the primary action. It is information the user needs later. Defer until the first drive exists.
5. **Post-login CLI output gives two next steps (observed).** Backup hint, then "Set a passphrase in the console under Settings" (SETUP-026-F3). Backup blocks `check`; the passphrase does not. One next step only.
6. **Repeated words inside single screens (observed, low).** Receipt dialog repeats "Without it nobody, including us, can open this drive" twice (F-SETUP-004-2, F-047-03). Granted summary names the granter three times in four lines (F-043-02); the worker summary repeats the same name three times (F-SETUP-023-03). Failure state shows the same error twice and three recovery controls Dismiss/Refresh/Try again (F-SETUP-005-2), and Dismiss leaves a stuck card (F-SETUP-005-1, high). Delete the second statement in each.

Already minimal: the pricing facts ("Free to start") were only flagged for a downloads inconsistency between landing table and `/pricing` (PROD-02 note), not for repetition. Not a redundancy problem.

## Overlapping Features (5 items)

1. **Second-agent access: `grant --verify` vs `credentials issue` vs recovery file on `/connect` vs manual API key.** Catalog 7.3 lists differing needs (browser, `delegate`, drive key shared). Observed: all four work except the manual key, which needs 19 actions (SETUP-047) and gives no drive key. Recommendation: name two canonical routes in docs and UI: "agent has a browser: `grant --verify`", "no browser (sandbox/CI): `credentials issue`". Demote the manual API-key path to the API keys tab labelled "for scripts that only call the API". Observed: delegate scope is required for both canonical routes and is hidden (see Hierarchy 1).
2. **Recovery file vs passphrase vs account seal vs credentials export bundle vs passkey.** These are different layers (storage for the drive key, browser unlock, agent-side verification, and a transport bundle), but users meet them as one choice. Observed evidence of confusion: the unlock dialog "Use a recovery file instead" loops back to "Use my passphrase instead" (F-SETUP-038-01, high); with no passphrase, Load-key lists the slower account-seal route first and the quick export-then-choose-file route last (F-SETUP-039-01); "recovery file" is the label although a credentials export or a pasted key also works (F-SETUP-022-03, F-SETUP-034-02, F-SETUP-039-03). Suspected root cause: the recovery file (`format=agent-drive-key-v1`) and the credentials bundle (`adcred1`) are two formats for one job. Consider one format that both CLI and console accept; at minimum make the CLI import the console recovery file (F-015-1).
3. **Automatic vs manual account seal.** Catalog 7.3: the CLI seals automatically and `account seal` is the only way to pin a first fingerprint. Observed: the Load-key dialog tells the owner to copy the fingerprint from Settings by hand though the console already knows it, and the copied seal command lacks `--fingerprint` so the first seal ends "unverified" (F-SETUP-035-02). The human-visible chore exists only because the console does not hand over the command with the fingerprint filled in. Fix the generated command; do not add a feature.
4. **Console drive-creation, Agents tab, Files "Connect an agent" and API keys page all describe connecting an agent with different completeness.** Observed: the API keys panel says "Run the CLI from the repository after building it" with origin-only `--api` (F-044-06, F-015-3, contradictions 44, 45); onboarding says click Approve. Consolidate to one shared component with one instruction text.
5. **"Traces" button next to "Capture..." button.** Observed in `SETUP-059/screenshots/step-1.png` (and the Files toolbar in `SETUP-035/step-7.png`): `Traces` opens the captured-traces folder, `Capture...` opens setup. Different jobs, near-identical names, adjacent. Rename: see Naming 5. Not a feature overlap once renamed.

Already minimal: Reverification and unlock for webhook capture work well once opened (SETUP-066 pass; SETUP-060 locked-drive unlock resumes automatically). No overlap finding there beyond wording.

## Hierarchy & IA (6 items)

1. **Delegate checkbox hidden in collapsed "Details" (observed, medium, three walkers).** `SETUP-044/screenshots/step-2.png` shows the checkbox "Let this agent add other agents to its drives" only after expanding Details, beneath MACHINE / ACCOUNT / DRIVE / ACCESS / WRITES / REQUESTED rows. F-SETUP-023-01, F-044-03, F-050-01: the summary does not mention it and the done card does not confirm it, and the CLI error says "(under 'Optional')" but no such heading exists. Everything the orchestrator story needs is below the fold. Promote it to the primary card when the request came from `grant`/an orchestrator, or at least show it in the summary line.
2. **Security-relevant information buried in Details (observed).** The Account row is only inside Details (F-013-2, F-SETUP-025-01), so a user with two accounts can approve into the wrong one. Same collapsed block holds "Use one of my drives instead (needs its recovery file)" (F-SETUP-022-03, F-SETUP-034-02). The page has no Deny control (F-013-1, SETUP-020); the only way to refuse is to close the tab. Show the account name in the header; add a Deny. This is the one place where adding an element is justified.
3. **"Settings" does not exist (observed, high).** CLI says "Set a passphrase in the console under Settings" (F-SETUP-035-01, F-SETUP-016-01). The sidebar has Files, Agents, API keys, Usage, Trash, Billing & limits, "Activity & deletion". The page behind the settings route is titled "Activity & deletion" and its "Passphrase unlock: Not set up. [Manage in Files]" card sits under an activity table (`SETUP-035/screenshots/step-2.png`). So the passphrase is set in Files, linked from Settings, which the CLI names. Three hops for one concept. Recommendation: say "Files > Unlock menu" in CLI text, or move the passphrase card to Files only and remove it from this page.
4. **Finder app undiscoverable (observed, medium).** F-PROD-01-4, F-SETUP-051-02: landing, footer, docs index, sidebar and llms.txt never mention it; the only link is in two paragraphs of the 48 KB `/docs/cli`. Same page contradicts itself on signing (F-PROD-01-5). For users who want a desktop mount, this is a primary feature at depth 3+. Add one line to the console empty state or the docs index; do not build a new surface.
5. **Quiet-vs-primary mismatch on `/connect`.** At 390px the Verification code input is about 165px wide so the typed code is clipped (F-009-2, F-SETUP-017-01, F-043-05); with Details open, Approve falls below 800px (F-SETUP-018-03). The primary action and the one required input degrade first. Layout issue, but it is an IA decision to put a label beside the input rather than above it.
6. **Console key menu has seven equal-weight buttons (observed, `SETUP-035/step-7.png`).** The two destructive-ish ones (Lock this browser, Forgot or exposed passphrase?) sit with routine ones. Group routine and rare actions; the walker also found the reset link absent from the stuck-user unlock dialog (F-SETUP-038-01). Reachability is wrong in both directions: reset is too deep when needed, the menu too long when not.

Already excellent: the `/connect` card hierarchy at desktop width (`SETUP-013/step-1.png`). One dominant orange "Approve agent", clear title "Connect nightly-sync?", a one-line summary "New encrypted drive · full access", and a revoke note. SETUP-016 walker agrees: "approval card clear, one dominant Approve". Do not redesign it; fix only the items in 1, 2, 5.

Already excellent: Files empty state with one primary Copy and three numbered steps (`SETUP-003/step-3-onboarding.png`), apart from the competing passphrase sentence in the header.

## Naming (7 items)

1. **Pairing code / verification code / fingerprint (observed, high).** Three concepts, two shapes: the 8-letter code (NTKN-JFWN) is called "pairing code" in the hero and console, "this code" on the page, "No pairing" tag on errors (F-SETUP-017-02); the 16-hex code is called "Verification code"; the account fingerprint has the same shape `a1b2 c3d4 e5f6 7890` (catalog contradiction 14). Observed consequence: using the login verification code as the fingerprint yields "does not match the account key the service returned (799c c0f8 98db 81e2)... the API may be answering with a different account key" (F-SETUP-035-03). Recommendation: "pairing code" (8 letters, matched by eye), "verification code" (16 hex, typed), "account key fingerprint" (always with the full label, with a Copy button; F-SETUP-036-03). Different shape or prefix for the fingerprint if possible.
2. **"Sandbox" means two things (catalog + observed).** Disposable machine running an agent (`AGENT_DRIVE_CREDENTIALS`) vs an Instabox workspace mounted on a desktop (`connect`). Observed: docs use SANDBOX_ID and never say what an Instabox sandbox is (F-SETUP-055-03), help lists `--sandbox` on `mounts add` which cannot register a live workspace (F-SETUP-055-01). Rename the Instabox one "workspace" in all CLI help and docs; keep "sandbox" for the credential case.
3. **One job, three names: "Give your first agent a home." / "CONNECT YOUR AGENT" / "Connect an agent" / "Give your agent a drive."** (catalog contradiction 5). Observed on the console: eyebrow "CONNECT YOUR AGENT", heading "Give your first agent a home." and top-right button "Connect an agent" (`SETUP-035/step-7.png`, `SETUP-003/step-3-onboarding.png`). Slogan heading plus plain button is acceptable; the landing "Give your agent a drive." adds a third. Pick the plain "Connect an agent" and let the slogan live only on the landing.
4. **Recovery file vs credentials export vs key vs bundle.** Button "Choose recovery file" / "Download recovery file again" / label "Drive key" / "Use one of my drives instead (needs its recovery file)" while a pasted key or `adcred1` bundle also works (F-SETUP-022-03, F-SETUP-039-03). Use "drive key file" for any of them, or accept all and say "recovery file or credentials export".
5. **Capture vs Traces (observed).** `Capture...` (toolbar), `Capture traces...` (drive menu), "Capture traces" (dialog), and a neighbouring `Traces` button that opens the folder (F-SETUP-059-1, screenshot `SETUP-059/step-1.png`). On a 390px screen the toolbar buttons are hidden and the action exists only in the drive-name dropdown. Rename: dialog opener "Set up trace capture", folder button "View traces". Keep one label for the same action.
6. **Unlocked vs Key loaded (observed).** Same chip shows "Unlocked" after passphrase setup (`SETUP-035/step-2`... `step-7.png`) and "Key loaded" after loading a recovery file (`SETUP-059/step-1.png`). May be deliberate (two states) but the chip menu text "Unlocked. Drives you added to your account open when you use them." does not say what Key loaded means. F-SETUP-040-02 also saw a green "Unlocked" on an agent-only drive where only the recovery file opens it. Unclear; confirm the two states are intended, then explain them in the menu.
7. **"Agent-only", "env", "stdout", "Settings", "Optional", "MISMATCH" jargon.** "Agent-only - never add this drive to passphrase unlock" (F-SETUP-040-03, F-047-05, F-SETUP-004-2); backup method "(env)" and "(stdout)"; "MISMATCH" means two things (catalog contradiction 37); "A same-origin request is required." (F-SETUP-063-1). Replace with plain labels or remove the tag from the user-facing text.

Already consistent: package name and install command match on every surface and on npm (PROD-01, PROD-03 notes). Do not touch.

## Top 5 recommendations (ordered by effect)

1. Fix the approval wording once, everywhere: say the human types the 16-hex verification code (7 independent walker findings); define pairing code / verification code / fingerprint as three named things. Duplicate Information 1 and 2, Naming 1.
2. Rewrite or remove "Settings": CLI says "console under Settings", the page is "Activity & deletion", and the passphrase actually lives in Files. Hierarchy 3. (F-SETUP-035-01, high.)
3. Surface what is hidden in `/connect` Details: show the account and the delegate checkbox on the main card, add a Deny. Hierarchy 1, 2.
4. Collapse the second-agent routes to two documented canonical paths (`grant --verify`, `credentials issue`) and make the CLI accept the console recovery file (F-015-1, high), so recovery file and `adcred1` stop being two formats for one job. Overlapping Features 1, 2.
5. One backup truth and one next step: unify the console and CLI backup records and show only the backup instruction after login, deferring the passphrase prompt until a drive exists. Duplicate Information 3, 4, 5.
